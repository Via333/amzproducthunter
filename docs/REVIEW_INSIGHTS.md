# 评论观点与未满足需求

## 定义

- 好评：用户已体验并认可的功能、品质或使用体验，低星评论也可能包含。
- 差评：现有产品执行不好的地方，如材质差、漏液、搅拌不匀。高星评论里的缺点同样计入。
- 痛点：某个用户在具体场景下需要完成的事，当前产品仍不能满足。有明确请求、使用受阻或替代操作证据；不是把差评换个名字。

同一条评论可有多个独立观点。不能把“易清洗”“希望早几年买到”判成未满足需求，不能把物流延误直接视为产品功能缺陷。已满足的需求是产品价值证据，不是新的市场缺口。

## 分析流程

1. 从研究目录 `reviews.csv` 读取完整评论，结合标题、具体 ASIN 和场景阅读，不使用截断的旧主题摘录代替完整上下文。
2. 按具体观点进行语义判断，写入该研究目录的 `review_insights.json`。当前没有自动语义模型服务；必须由研究代理阅读原文后产出结构化判断。不要用词表或星级填充看似已分析的结果。
3. 每项观点保留中文结论和逐条引用；痛点还须说明需要什么、使用场景、尚未满足、需求依据及仍需验证的内容。关注相反证据、其他型号已解决的功能和用户可能误解的用法。
4. 运行 `compile_review_insights` 校验引用，再用 `build_product_research_pages.py` 重建页面。校验只证明引用匹配，不代替观点语义审核。
5. 未分析原文保留在展开区。其他研究未生成新格式时，不按旧星级和关键词结果自动填入三个页签。旧 `demand_analysis.csv` 保留为历史主题统计，不改变已有市场评分或研究原始数据。

## 数据约定

顶层字段：`schema_version: 2`、`source_snapshot`、`reviewed_on`、`method`、`insights`。

`source_snapshot` 使用 `review_insights.snapshot_hash(reviews)`，评论内容或评分/日期变化会使旧观点失效，需重新核验。核验日期不是采集日期。

每项观点字段：

- `id`：研究内唯一标识。
- `kind`：`positive`、`negative` 或 `pain`，不由评分推导。
- `summary_zh`：具体中文结论，不能仅为“清洗”“性能”等主题词。
- `evidence`：非空引用列表，元素包含 `asin`、`review_title`、`quote`、`translation_zh`。默认引用 `review_text`；如引用标题需显式 `field: review_title`。
- `pain` 额外字段：`need_zh`、`scenario_zh`、`gap_zh`、`validation_zh`、`need_basis`，后者为 `explicit_request` 或 `blocked_workflow`。

引用必须精确匹配当前快照；找不到或无法唯一定位时，整项观点保留待核验。不要通过修改原文让引用校验通过。

## 统计边界

- 页签数量是已整理的观点数，不是评论条数。
- “已核引用”只统计该观点已选择的证据，按标题和正文合并重复文本；跨 ASIN 相同文本不会重复增加数量。
- 同文合并不代表识别了独立买家，选取引用也不代表穷尽所有提及频次。
- 单条评论可证明存在一个需求线索，不能证明市场规模、支付意愿或需求普遍性。供应商可行性、利润、适用合规、专利与设计取舍仍需独立核验。
